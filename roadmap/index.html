    Roadmap¶

    What we are building, in the order we build it, and what each release has delivered — the open work at the top, the releases below it.

    The current plan is security and stability. It is built in waves: first make upgrades safe, then make the breaking changes while few sites depend on today's shapes, then harden the network, then stability, then new capabilities. A filled marker means work in the wave is done and waits for the next release; a hollow one, nothing in it is done yet. Every two weeks the next version is cut for staging and reaches production two weeks later. Press + on a card for its groups and their issues.

    Wave 6

    Site fabric and user experience

    The physical site and how an operator sees and runs it. Not ordered by upgrade risk like Waves 0–4: these two groups are designed together — the fabric is what the physical view shows and changes.

    3 groups 15 open
    Groups and issues

    G6.1 Switching fabric, WAN, ISP & site operations

    The links a site stands on: node uplinks (a bond under lan, #40), switch ports and trunks kept in line with the zones (#668, #697, #706, #731), the WAN and the ISP (public DNS that follows the WAN, #383, #830; mail when the ISP blocks port 25, #125). Switch setup needs a systematic model, at install and on day 2. Operating the site belongs here too: a service desk (#63) and a SIEM (#843, Wazuh the best candidate). Linked to G6.2: the physical view shows and later changes it.

    • #383 Keep wildcard public DNS current on dynamic WAN
    • #830 environment-manager: no verb creates the public DNS record
    • #125 Mail relay via M365 Graph API
    • #668 A machine's zone is recorded, not enforced
    • #697 Node lan trunks and their switch ports are set once at install, maintained by nothing
    • #706 A wireless device zone cannot be checked against its SSID
    • #158 Multi-NIC module firewall rules
    • #236 RADIUS MAC Auth Bypass: a device's VLAN from its MAC, on Wi-Fi and wired ports
    • #63 Service desk tooling spike
    • #843 Create a SIEM for TAPPaaS
    • #883 A debug bundle for support: the log and an anonymized ~/config, attached to the failure mail

    G6.2 User interface & physical view

    A general TAPPaaS user experience, starting with a physical view of the site: nodes, bonds, switches and ports, APs, WAN and satellite, with zones, guests and live state on them (#839; homelable as a starting point), designed first in a spike and an ADR (#844). The service catalog (#183) and Backstage (#91) are decided against it. Linked to G6.1.

    • #885 console: agents act through the identity gate
    • #886 console: a security view of the SIEM's alerts
    • #887 console: a status page and badges for the site's users

    G6.3 Data model

    The meta model of the configuration is written down in src/DATAMODEL.md (2026-10-22: every JSON, which field names which object, and seven places where the model says one thing twice). The operator decided to fix the first four and park the rest (#866). Where a thing is becomes two things, a location and a placement, by ADR-036 (Accepted 2026-10-23). Linked to G6.2: the console's Physical view draws what this group models.

    • #866 Data model: parked simplifications (backup cascade, module placement, module:service)

      TAPPaaS 2.3

      A site turns it on with site.json ipv6: true (default false): each zone gets a /64 from the WAN's prefix, every VM's name resolves to its IPv6 address too, the firewall rules cover both families, names published through Caddy answer over IPv6 inside the site, and Caddy is reachable from the internet over IPv6 — publish the address ipv6-manager reports as the AAAA; everything still works over IPv4, and switching it off withdraws IPv6 cleanly.

      v2.3 in staging
      What it carried, by group

      Tag v2.3, cut into staging 2026-10-25 by a release-train boundary.

      IPv6, opt-in per site. A site turns it on with site.json ipv6: true (default false): each zone gets a /64 from the WAN's prefix, every VM's name resolves to its IPv6 address too, the firewall rules cover both families, names published through Caddy answer over IPv6 inside the site, and Caddy is reachable from the internet over IPv6 — publish the address ipv6-manager reports as the AAAA; everything still works over IPv4, and switching it off withdraws IPv6 cleanly. The first sweep after upgrading turns IPv6 off on the firewall — inbound IPv6 dropped, DNS over IPv4 only — unless the site sets site-manager site modify --ipv6 true first. Existing zones are given an IPv6 number (migration 0016); it does nothing while ipv6 is false. See IPv6 and Firewall Rules on tappaas.org.

      Firewall and DNS. Unbound validates DNSSEC: the first sweep turns it on (site.json dnssec, default true; set it false to opt out); internal and published names are unaffected. A zone can share mDNS discovery with other zones ("mdns": true; discovery only, reach is still the zone rules). A client zone can serve several environments (serves as a list, network-manager bind --add). A module's aliasType can now be changed and is applied in place; ports on a module without network:rules is documentation and no longer warns. rules-manager overlaps reports shadowed, redundant and conflicting rules, and a pinhole a zone's access-to already covers is no longer written. Every zone with internet access now also blocks CGNAT, link-local and the firewall's own addresses, and a module's egress to: internet excludes the site.

      The console. A web console at console.<domain>, behind the Authentik sign-in and reachable from the management zone and the admin VPN only: the site's physical and logical views, its modules, updates and repositories, and every manager verb as a job that is previewed before it runs; a destructive verb asks for the object's name. Before identity is installed, a one-time setup token on the mothership opens it for the rest of the install.

      Signed releases. A checkout on a staging or production branch moves only to a release tag signed by a key that the last verified release lists, and never backwards; a fresh clone starts from a signed introduction. The health check reports every repository's signature state and keys about to expire.

      Cluster. A second corosync link; a QDevice gives a two-node cluster its third vote, and node add warns when a cluster has only two. USB network adapters can join the LAN bond, and node network set --wan-port chooses the WAN port. HA places a guest only on nodes that carry every bridge it uses and no longer moves a host-CPU guest live onto an older CPU. The sweep refuses an over-committed node, and guest disks grow automatically.

      Modules. New: Karakeep (bookmarks and read-later, tagged by the AI stack), Woodpecker CI beside Forgejo, lazysite (a Markdown website from a Forgejo repository) and Project N.O.M.A.D. (an offline knowledge library). Jellyfin moves to 12.2 with the maintained SSO plugin and is published without the identity gate so its apps can sign in; its database is migrated on the first start and cannot go back — the pre-update snapshot is the way back. CrowdSec on the firewall bans repeated failed logins and probing on published names. A route can be limited to paths, to zones and to a provider's source ranges. module-manager gains suspend and resume, add-stack, and migration by changing a module's node.

      Security. Images move to current releases (Authentik 2026.8.5, Karakeep 0.34.1, Meilisearch 1.55 — its index is converted on the first start — and lazysite 0.16.0), and the CVE scan now sees native libraries bundled inside Python packages. Two risks are documented in their install guides: the console believes the identity gate's headers from the firewall's address, so the management zone must hold only TAPPaaS's own machines; and NOMAD's Command Center has no sign-in and controls the VM's Docker. A guest moved live onto an older CPU may run without some CPU-side mitigations until it next reboots.
